## 0. 理念（一句话）

**在我这台机器能跑出的最优配置下，本地模型与云端模型的多维度能力对照。**

### 三个关键转变

| | 旧 | 新 |
|---|---|---|
| 结论形态 | 一个加权总分排名 | **架构 × 场景 矩阵，每格一个本机最优配置** |
| 主问题 | 谁最强 | **这一档本地打得过云端吗，差在哪** |
| 受控对照 | 目的本身 | **手段**（选出最优 + 确认没变笨） |

### 为什么必须变（三条硬证据）

1. **参数线已终结**。文件二用 141 组实测把参数空间走完，原文：「参数优化本身已经没有空间了」。
   继续测参数是在验证旧结论，不是产出新结论。
2. **「最好」不止一个**。本机三档模型各有场景：
   MoE-35B ×6 · 稠密-27B ×6 · 稠密-9B ×1。单一冠军是错的问题。
3. **旧数字不可信**。文件二自己写：20 题测出 PTQ1 与 PQ2 都是 95%，
   「这是样本太小（5% 粒度）造成的假象」。

## 1. 形态：软件为主 + skill 做入口

- **软件**负责：起停引擎、跑题、判分、统计、出矩阵表。受控对照要重复几十组，这是程序干的活。
- **skill** 负责：讲清方法、判据、怎么读表、什么结论不能下。
- **分工边界**：参数与速度归 `llm-param-tune`；能力与选型归本项目。两份不重叠。

# 附：2026-10-31 思路检验后的两处修正

> 本节由主智能体自行检验得出，**推翻了初版计划中的两个关键假设**。执行时以本节为准。

## 修正 ① 分维度样本量：105 → 390 题/配置

**初版错误**：把「每配置 ≥100 题」理解成「总计 105 题、四维各 25 题」。

**实测功率**（配对相关模型，2000 次模拟，McNemar 精确检验 α=0.05）：

| n | Δ5pp | Δ10pp | Δ15pp | Δ20pp |
|---:|---:|---:|---:|---:|
| 25 | 0% | **2%** | 13% | **34%** |
| 50 | 2% | 31% | 73% | 94% |
| 105 | 32% | 92% | 100% | 100% |
| 200 | 88% | 100% | 100% | 100% |

**n=25 时 20pp 真实差距只有 34% 概率被检出** —— 等于测不出来，会重演文件二「两个引擎都 95%」的假象。

**修正后分配（390 题/配置）**：

| 块 | 题数 | llama.cpp 耗时 |
|---|---:|---:|
| 通用准确率 | 100 | 13.6 min |
| 工具调用 | 100 | 14.4 min |
| 抗幻觉 | 100 | 10.4 min |
| 长上下文 16k/64k/128k | 30+30+30 | 99.9 min |
| **合计** | **390** | **138.2 min (2.30 h)** |

**总规模**：25 配置 × 平均 ≈ **81.1 小时**（约 10 个工作日独占 GPU）。
用户 2026-10-31 决策：**接受 81 小时，但必须分批执行。**

## 修正 ② 胜者诅咒：冠军分数需分半确认

**问题**：25 个配置里挑最高分，报告分数天生虚高。

| 候选数 | 虚高幅度 |
|---:|---:|
| 2 | +2.4 pp |
| 5 | +5.1 pp |
| 10 | +6.7 pp |
| **25** | **+8.5 pp** |

**后果**：直接拿冠军分数与云端比，本地被系统性高估 8.5pp，结论方向可能错。

**已验证解法 —— 分半选择法**：

```
选择阶段：用一半题（195 题）在 25 个配置里挑冠军
确认阶段：用另一半题（195 题）单独测该冠军，只报这个分数
```

模拟验证：选择半集最高分 **82.0%** → 确认半集 **70.0%**（真值 70.0%，完全校正）。

**实现要求**：题集必须能稳定二分（固定 seed），且两半不可重叠。选中配置的最终分数**只来自确认半集**。

# 附二：2026-10-31 视频研究后的判据修订

> 来源：BV1Hrxe6YEMC（鹈鹕）、BV11LWw6VEe5（Flash 模型横评）。
> 这两条视频指出的问题，经数据核实后**部分成立**，据此修订判据。

## 一、核实结论（不是照抄视频）

| 视频论点 | 我们的情况 | 判断 |
|---|---|---|
| 公开基准已泄漏，刷题失效 | 60.3% 是公开基准，全部标 high risk | 成立 |
| 各基准考察能力高度重叠 | 选择题仅 28.3%，四维题型不同 | **不成立** |
| 静态考卷跟不上动态实战 | 「需要动手」的题仅 9.8% | **成立** |
| 跑分与日常体验割裂 | 真实会话来源仅 32 题（1.6%） | **成立** |
| 可用性应计入判据 | 质量与速度分开报 | 成立 |

## 二、修订 1：可用性改为「超时标注」，不是「一刀切 0 分」

**否决的方案**：跑不完 = 0 分。
**理由（用户判断，正确）**：本地模型存在「时长久但质量高」的真实形态，一刀切 0 分会误杀它，
而这恰恰是本地相对云端的真实优势。

**采用的方案**：

```
每个任务设超时上限 T（默认 300 秒，可配置）
  - 在 T 内完成     -> status=ok,   计入质量分
  - 超过 T 被截断   -> status=timeout, 质量分照常记（若已产出有效结果）
                      同时单独记 timeout_rate，并在报告里显式标注
  - 超过 T 且无产出 -> status=failed,  该题不计入质量分母（走 mark_error）
```

**报告呈现**：每个模型/配置一行，四列并存：

| 配置 | 质量分 | 覆盖率 | 超时率 | 中位耗时 |
|---|---:|---:|---:|---:|

**判读规则**：
- 超时率 < 5%：质量分可直接横向比较
- 超时率 5-20%：质量分需附「超时率」一起读，不能单看分数
- 超时率 > 20%：标「可用性受限」，该配置不建议作主力，但**分数仍然保留**

**这样做的价值**：能区分出三种模型——
1. 快且准（理想主力）
2. **慢但准（本地特色，可用但要接受等待）**
3. 快但不准 / 慢且不准（淘汰）

一刀切 0 分会把第 2 类和第 3 类混为一谈。

## 三、修订 2：加「多轮动态轴」

**形态**：给模型一个真实小仓库 + 一组红测试，连续改 3 轮，看测试能否转绿。
**判据**：`最终测试是否全绿` + `用了几轮` + `总耗时`。
**成本**：20 题 × 3 轮 = **14.5 分钟**（占单配置约 11%）。

**为什么不是视频里那种红绿灯仿真**：
- 那是闭源云端横评，单场几百轮；本地 8G 卡跑 500 轮要 2 小时/配置
- 我们要的是「本地最优 vs 云端」，不是云端性价比
- **但最小可行形态是可行的**：3 轮 × 20 题只要 15 分钟

## 四、修订 3：真实任务轴用「可交付」判分

**旧**：回答里含关键词 / 检查项通过。
**新**：**能不能真的交付**。

| 任务类型 | 判据 |
|---|---|
| 修 bug | 测试从红转绿（真跑） |
| 写脚本 | 脚本能跑通并产出预期输出 |
| 改配置 | 校验器打印 OK |
| 数据分析 | 结果文件能生成且数值正确 |

**关键**：不判「说得好不好」，判「做完没做完」。

## 六、视频本身的局限（不照抄的理由）

1. **人工横评不可复现**：红绿灯视频评论区高赞指出「豆包和 MIMO 搞反了」，
   这正是我们做自动化评测的价值。
2. **它是闭源云端横评**：7 个模型全是 API，与「本地最优 vs 云端」不是同一个问题。
3. **鹈鹕题已失效**：出题人自己公开劝大家别再拿它比能力。

我们学的是**判据设计**（可用性、动态、可交付），不是它的题目。
