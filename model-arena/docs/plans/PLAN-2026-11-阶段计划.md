## 一、这一阶段的核心问题

**判分器改动已经做过三轮，但「重算」本身没有可信链。**

本会话修了 4 个同源 bug，全都指向同一件事：

| # | bug | 后果 | 状态 |
|---|---|---|---|
| 1 | `run_checkers([])` 返回 `(True, [])` | D5 的 300 条 IFEval 题任何回答都判对 | 已修 |
| 2 | `CORE_FILES` 漏 `checkers.py` | 改判分器不改指纹，静默重算无痕 | 已修 |
| 3 | `rescore` 对 `LEVEL_*` 一条都没重算却写 `_rescored` | 假重算，掩盖 bug 1 | 已修 |
| 4 | `rescore` 漏 `compression.py`；**且从不写 `judge_version`** | 47 个维度格子指纹全部过期 | **未修** |

第 4 条的实测证据：

```
current fingerprints: {'core': '78900cb2d0ae', ...}
维度格子总数: ok=0  旧指纹=47  无指纹=0
```

即：**榜单上没有一个格子能证明自己是用当前判分器算的。**
本会话上一轮生成的那 164 个 `_rescored.json`，有 82 个根本没写 `judge_version`，
73 个写着旧指纹 `e33116660747`。它们刷新了判决，却没有刷新"这批数字由谁产生"。

> 这正是本项目铁律 3 的反面：改判分器必须重跑/重算历史数据。
> 现在重算能力有了，但**重算的产物无法自证**，等于还差最后一步。

## 二、阶段目标（按依赖顺序，不按重要性）

### P1 重算可信链（阻塞项，纯 CPU，约 1 小时）

没有它，后面所有数字都无法判断新旧。

- [ ] `rescore.py` 在写 `_rescored.json` 时写入当前 `judge_version`（core + 对应 suite）
- [ ] `build_report.py` 读到指纹不一致的格子时，**不要静默采用**，要在报告里标 `⚠ 旧指纹`
- [ ] 新增回归测试：重算后的文件必须带当前指纹；指纹不符的格子必须被标记
- [ ] 重新生成全部 `_rescored`，让 47 个格子都带上 `78900cb2d0ae`

**验收**：`leaderboard.json` 里 `ok == 47`，旧指纹 0 个。

### P2 覆盖缺口（需要 GPU，按模型逐个排期）

加权维度共 8 个（`config/weights.json` 的 `scored`），12 个模型里只有 **4 个**跑满 8 个：

| 模型 | 跑满 | 缺什么 |
|---|---|---|
| deepseek-flash | 8/8 | — |
| kv17-bonsai2t5 | 8/8 | D7 只有 n=2，实际等于没测 |
| Qwen3.6-35B-APEX | 8/8 | — |
| mock-model-80pct | 8/8 | （假端点，对照用） |
| Qwen3.5-9B | 6/8 | D2、D7 |
| deepseek-chat | 6/8 | D7、D9，且多处 n<40 |
| Qwen3.5-9B-128k | 1/8 | 只有 D7 n=16 |
| 其余 4 个 | 0-1/8 | 只有零星试跑 |

**这里有个必须先解决的判断**：D7（长上下文）成本 14.69 元/次，占全量九成。
给 8 个模型补满 D7 是 100+ 元，而现有 5 个跑过 D7 的模型里，
本地模型也只有 2 个拿到了 n>50。**补覆盖之前要先决定：D7 到底进不进加权总分。**

- 若进：要么接受高成本，要么把 D7 从加权里拆出去单列。
- 若不进：榜单少一列，但其余 7 维覆盖成本可以大幅下降。

这一条我不替你定，它是产品决策。

### P3 判分器测试覆盖（纯 CPU）

`lcb_judge.py` 是**唯一 0 引用的判分器**（其余 11 个都被至少一处测试引用）。
它判 D4 的 LiveCodeBench 子类，37 题。现有测试只通过 `public_judge` 间接覆盖它，
没有直接断言。

- [ ] 给 `lcb_judge` 加直接测试：正确程序判对 / 错误程序判错 / 无代码不崩 / 超时不崩
- [ ] 检查 `rejudge.py` 与 `rescore.py` 的判分分支是否已经重复（两套重算入口容易各自漂移）

### P4 D12 的区分力（改题库设计，需谨慎）

现状：压缩比 **8.3%**（本会话实测 `doc 6394 chars → summary 530 chars`），
Qwen3.5-9B 压缩前后都是 24/24。**这个维度目前测不出任何模型差异。**

三个可选方向（都需要你先拍板，因为会推翻现有 D12 结论）：

1. **降摘要信息量**：把目标编号也压掉一部分，让模型必须从上下文推断，而不是照抄。
2. **提高压缩比要求**：现在 8.3%，压到 4% 以下再测。
3. **保持现状，承认它只能测"有没有明显崩坏"**，在文档里写清它不是区分性维度。

## 三、不做的事（明确划出）

- **不重跑 D12 历史文件**。场景由 seed 生成，`build_scenario` 改过之后同 seed 不再复现同一场景
  （实测 seed 20261101 当年是「石工程师」，现在是「江总监」）。离线重算会给出假分数，
  `rescore.py` 已硬性拒绝。要更新 D12 只能重跑模型。
- **不动 D11/D12 进榜**。它们不在 `weights.json`，不参与加权总分，这是设计如此，不是缺陷。
- **不改 `judge_version` 的分层结构**。CORE + 按 suite 分层是刻意设计（避免 LCB 的改动
  把 D2..D9 全标成过期），只需要把漏掉的文件补进去。
