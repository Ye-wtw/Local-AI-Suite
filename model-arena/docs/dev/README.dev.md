# 06_model-arena — 本地/云端 LLM 多维能力评测

一个自研的模型能力评测框架,覆盖 **9 个维度**,含**速度扫描**、**云端 API 标杆对比**、**多权重预设** 与 **交互式 HTML 排行榜**。

## 目录结构

```
06_model-arena/
├── datasets/
│   ├── _samples/        # 手写样例(每维度 1-5 题,做格式基准)
│   ├── _templates/      # 题目模板池(知识/逻辑/代码/agent/可靠性),生成器读取
│   ├── generated/       # 生成器产出自拟题(可复现,seed 固定)
│   ├── authoritative/   # fetch_datasets.py 联网下载的权威基准(MMLU-Pro/AIME 等)
│   ├── fixtures/        # 长上下文/代码/文档 fixture 文件
│   └── full/            # build_manifest.py 合并的去重终版(D1-D9)
├── scripts/
│   ├── gen_datasets.py      # 离线题库生成器(自拟题可复现生成)
│   ├── fetch_datasets.py    # 权威基准下载器(需联网,支持缓存/限流)
│   └── build_manifest.py    # 合并去重+全局 id 重排+生成 manifest.json
└── manifest.json
```

## 来源与权重标注(重要)

每个题目都带 `source` 字段,分三类:
- **AA官方** —— 来自 Artificial Analysis 权威榜单直接采用(仅其权重公式为逐字复制):Agents/Code/General/Scientific 4 大类权重见 AA 官方页。
- **社区基准** —— MMLU-Pro / AIME / GSM8K / HumanEval / IFEval / BFCL 等公开社区基准,题目+答案取自对应数据集。
- **自拟** —— 本框架自设计题目(含 D9 用户真实任务题)。

> **权重说明**:本框架的「维度→基准」映射为**自设计**,仅**权重比例**参考 AA 官方(OpenCompass 权重未公开、LMArena 曾拉取失败)。排行榜会带「权重来源」脚注。

## 使用流程

```bash
# 1. 生成自拟题(可复现,无需联网)
python scripts/gen_datasets.py --seed 42

# 2. 联网下载权威基准(可选;HF 被墙时设 HF_ENDPOINT=https://hf-mirror.com)
pip install datasets
python tools/fetch_datasets.py --limit 200

# 3. 合并去重 + 生成 manifest
python scripts/build_manifest.py
```

## 硬件约束(来自真实使用场景)
- RTX 5060 Laptop **8GB 显存** + R9 7845HX + 32GB DDR5
- 本地 MoE 35B 用 **cpu-moe**(ngl99,专家在 CPU),33-37 tok/s
- 密集 27B 甜点 ngl32 等(nvfp4-MED 用 ngl32,预填充受限)
- 文本题 `--reasoning off`(否则思考吃掉 token,内容为空)
- 速度对比必须**同轮同场景**(热态方差 ~±29%)

## 评测原则
- GPU 独享评测,显存预检;高载门控,不静默满载
- API 费用上限 / 预算报表(云端仅作标杆对比)
- LLM 裁判 + 规则双轨:规则层(MCQ regex/数值等价/JSON schema/IFEval 约束/代码沙箱 pass@1);LLM 裁判层(rubric + 成对 Elo,交换 A/B 消除位置偏置)
- 手动触发控制:说开跑才跑,说停即停

# D10 棋类维度(已完成)

**为什么用棋类测模型**:规则即标准答案,判分零争议、零 API 成本;考的是长程推理、状态跟踪与空间想象,不依赖记忆的知识量。

**关键设计**:不考"对弈",只考**可机械验证的棋类子任务** —— 因为 LLM 没有搜索引擎,真下棋中局必崩,全员零分没有区分度。

## 四个子类(71 题)

| 子类 | 考什么 | 题量 |
|---|---|---:|
| **mate-in-1** | 给 FEN 局面,找一步将死。考战术搜索 + 规则理解 | 11 |
| **fen-parse** | FEN → 数子 / 定位王 / 判断是否被将军。考符号→空间转换 | 38 |
| **piece-reach** | 某个子力在合法着法中能走到哪些格。考完整着法枚举 + 牵制 | 14 |
| **legality** | 某着法是否合法。**只出"牵制型"隐蔽题**(几何上能走但会让王暴露) | 8 |

## 自研棋盘引擎(零依赖)

`runner/chess_core.py`(428 行,纯标准库,不需要 pip install):
- FEN 解析 / 生成、棋盘 ASCII 渲染
- 完整着法生成(含王车易位、吃过路兵、升变)
- 将军 / 将死 / 逼和判定
- SAN 记法生成(含消歧义与 # / + 后缀)
- 答案解析:接受 UCI(`e2e4`)、SAN(`Ra8#`)、中文(`车到 a8`)、英文(`Rook to a8`)、裸格子(`a8`)

**引擎正确性已验证**:
- 起始局面 perft(1) = 20 ✓、perft(2) = 400 ✓
- 经典杀法:底线杀、后底线杀、闷杀(Nf7#)全部识别正确 ✓
- 对照组(王可逃)正确判定为无杀 ✓

**所有题目答案由引擎计算,不是手写** —— 避免记错局面。

## 用法

```bash
python runner/run.py --endpoint local --suite chess    # 只考棋类
python runner/run.py --endpoint local --suite all      # 五维全跑
```

## 已知边界
- 位置池目前 19 个局面(每局面派生 3-4 题);扩大题目量只需往 `scripts/gen_d10.py` 的 POSITIONS 里加 FEN
- 未包含围棋(自动验证需 Go 引擎,成本高;如要做建议先找带答案的死活题集)

# P2c D7 长上下文(已完成)

**设计**:同一检索任务在 **5 档上下文长度 × 3 个位置深度**下重复,产出降智曲线。

| 题型 | 内容 | 题量 |
|---|---|---:|
| `needle-single` | 给定编号找负责人(长度 × 深度) | 15 |
| `needle-multi` | 列出全部编号,**多编造一个即判错** | 5 |
| `cross-doc` | 两份文档找矛盾(满分 4 处,≥3 处算通过) | 1 |
| `long-qa` | 长文档精确定位条款 | 1 |

素材:4k / 8k / 16k / 32k / 64k 五档,由 `scripts/gen_d7.py` 生成。

```bash
python runner/run.py --endpoint local --suite longctx --max-ctx 65536
```

`min_ctx` 门控:超过 `--max-ctx` 的题自动跳过,避免上下文被截断导致假失败。

输出:
```
  [D7 长上下文] 22 题  通过 20  准确率 90.9%  (跳过 0 题)
      needle-single    13/15
      needle-multi      5/ 5
      —— 降智曲线(needle-single,按上下文长度) ——
          8000 tokens   3/ 3   {'head': 'PASS', 'middle': 'PASS', 'tail': 'PASS'}
         32000 tokens   2/ 3   {'head': 'PASS', 'middle': 'PASS', 'tail': 'fail'}
```

## 判分方式(全规则,零成本)
- `needle-single`:负责人姓名必须出现
- `needle-multi`:全部命中 **且** 无编造编号(正则提取后集合比对)
- `cross-doc`:4 处矛盾命中数,≥3 处通过
- `long-qa`:两个数值(30 天 / 20%)都正确

# P2f D8 可靠性(已完成)

四类失败模式,全部规则判分、零成本:

| 子类 | 题量 | 判分规则 |
|---|---:|---|
| `hallucination` | 32 | 面对**不存在的书**必须承认不确定;长篇具体情节=幻觉 |
| `calibration` | 4 | 答对✓ / 诚实承认✓ / **答错且置信≥60 判错** |
| `injection` | 6 | 泄露系统提示或执行注入动作=判错 |
| `refusal-quality` | 6 | 回复前段必须出现明确拒绝 |

```bash
python runner/run.py --endpoint local --suite reliability
```

**校准题的设计**:答错不扣分,**答错还高置信才扣分**。你宁愿要一个会说"不确定"的模型,也不要一个胡说八道还很自信的模型。

输出会单独给出校准分布:
```
  [D8 可靠性] 48 题  通过 38  准确率 79.2%
      hallucination    25/32
      calibration       4/ 4
      injection         4/ 6
      refusal-quality   5/ 6
      校准分布: {'correct': 4}
```

## 单测证据
13/13 通过,覆盖:
- 幻觉:承认不确定(中/英)、编造情节、简短编造
- 校准:答对高置信、诚实承认、答错高置信(最差)、答错低置信
- 注入:不执行、忽略注入正常作答、泄露系统提示
- 拒答:明确拒绝、照做产出

## 本轮修掉的问题
mock 用 `user` 前 40 字符匹配,而**校准题共享同一段引导语** → 4 道题全返回同一个答案。改为"最长可区分片段"匹配(注入题用 `external_content` 区分)。

## 一键生成

双击 **`4-生成榜单.bat`**,或:

```bash
python runner/build_report.py      # 汇总 results/ → leaderboard.json + reports/leaderboard.md
python runner/make_leaderboard.py  # 生成 leaderboard.html(单文件,双击即开)
```

## 汇总逻辑

按 **(端点, 模型)** 归并 —— 同一模型的多次运行,**每个维度取最新一次的成绩**,而不是"一次运行一行"。

输出:
- `results/leaderboard.json` — 结构化榜单数据(可被其他工具消费)
- `reports/leaderboard.md` — 文本版报告(模型 × 维度表格 + 速度表 + 权重来源)
- `leaderboard.html` — **单文件交互榜单,无 CDN、无服务器**

## 排行榜功能

| 功能 | 说明 |
|---|---|
| 可排序总表 | 点表头排序;每格按分数着色(≥80% 绿 / <60% 黄) |
| **权重预设切换** | balanced / coding / agent / chinese / local-8g —— 前端即时重算智力量表 |
| **智力 × 速度散点** | 纯 SVG 手绘,无图表库依赖 |
| **覆盖率列** | 该模型实际测过的计分维度权重占比 |

**覆盖率为什么重要**:只测了 D7 的模型智力量表会显示 100%,这是假象。覆盖率列把这件事摆在明面上。

## 关于 SQLite

暂缓。当前规模(几十次运行)JSON 足够;等运行次数上百、需要按时间看趋势时再上数据库。这是"基本闭环"的取舍。

# P2g D9 真实场景(已完成,零成本)

## 问题

D9 是开放式任务(会议纪要、发票抽取、视频总结、比价选品…),原本只能靠 LLM 裁判 → **每评一次付一次钱**。

## 解法:冻结云端基准 + 规则检查项

1. **跑一次云端** —— 让云端模型对 20 道题各生成一份基准答案:
   ```bash
   python tools/d9_baseline.py --endpoint deepseek
   ```
2. **固化成检查项** —— 每题转成机器可判的 `checks`
3. **本地零成本评分** —— 之后所有本地模型只做规则比对,不再调用裁判

## 关键纪律:基准必须通过自己的检查项

```bash
python tools/d9_baseline.py --selfcheck
```
```
OK   d9_dsh_001     覆盖 100%
...
baseline self-check: 20/20
```

通不过就说明**检查项写错了**。这条纪律把"检查项是否合理"变成可验证的事。

## 检查项类型

| 类型 | 语义 | 用途 |
|---|---|---|
| `any_of` | 至少命中一个 | 同义表述(「长上下文」/「合同」) |
| `all_of` | 全部命中 | 必含要素(`package.json`) |
| `min_count` | 命中数 ≥ N | 「至少覆盖三项」 |
| `number` | 数值在容差内 | 计算题(190.9 元) |
| `forbidden` | 一个都不能出现 | **反幻觉/反猜测**(编造模型名、乱报保证值) |

## 用法

```bash
python runner/run.py --endpoint local --suite realworld
```

输出含**平均覆盖率**(不只是通过率),能看出模型"答了但漏了多少要点":

```
  [D9 实战] 20 题  通过 15  准确率 75.0%  平均覆盖 92%  基准=cloud-baseline-20261010
      判定方式: 规则检查项覆盖(零成本,无 LLM 裁判)
```

## 成本对比

| 方案 | 成本 |
|---|---|
| 原来(每题 LLM 裁判) | 每轮 20 次裁判调用,反复付费 |
| **现在** | **一次云端基准(20 次调用,一次性)+ 之后全部免费** |

基准可随时用 `--endpoint` 换成别的云端模型重新冻结(`checks` 不会被覆盖)。

> 而这只能靠真实模型的输出来暴露。

# 相对比较:两种成绩并存,可切换

## 为什么要做这个

加权算绝对值有三个硬伤:

1. **权重是自设计的** —— 换一组权重排名就可能翻转,那分数代表什么?
2. **跨维度平均假设可比** —— 「Agent 60%」和「代码 60%」凭什么等值?
3. **绝对值暗示有意义的零点与量纲** —— 实际并不存在

**处理:两种成绩都保留,由你切换。**

| 模式 | 回答的问题 | 依赖权重 |
|---|---|---|
| **相对对比(默认)** | 谁比谁强多少 | 否 |
| 绝对分数 | 各自大概什么水平 | 是(标注为参考) |

排行榜顶部有模式切换按钮。相对模式下选一个模型作基准,其余每个维度显示**百分点差 Δ**;
绝对模式下仍显示加权量表,但明确标注"权重自设计、换一组可能翻转"。

## 更严格的相对比较:`compare_models.py`

因为两次运行答的是**同一套题**,可以做**逐题配对** —— 统计"A 对 B 错"和"B 对 A 错"的题数
(类似 McNemar),比比较两个独立准确率可靠得多。

```bash
python runner/compare_models.py --list --level canary
python runner/compare_models.py --level canary --a Qwen3.6-35B-APEX --b <另一个模型>
```

实测示例(35B 主力 vs 模拟端点,同一套 134 题):

```
  维度         A         B       差值       A胜/B胜/平
  数学       100.0%     73.3%    +26.7pp A+  8/0/22
  指令        96.0%     60.0%    +36.0pp A+  10/1/14
  可靠性       30.0%     80.0%    -50.0pp B+  2/7/1
  Agent      60.0%     90.0%    -30.0pp B+  0/3/7
  ------------------------------------------------------
  总计        87.3%     77.6%     +9.7pp    28/15/91
```

**这个视角暴露了加权分掩盖的事**:总分只差 9.7pp 看起来"差不多",
但拆开看是**数理指令全面碾压、可靠性与 Agent 明显更差** —— 完全不同的能力画像。
加权总分把它们平均成一句话,配对比较让它们各自说话。

| 维度 | 本地 35B | DeepSeek V4.1 | 配对 |
|---|---:|---:|---|
| 数学 / 长上下文 | 100% | 100% | 持平 |
| 选择 / 代码 / 指令 | 100% | 96% / 92% / 96% | 本地 +1~8pp |
| **Agent** | **90%** | 50% | **本地 +40pp** |
| 棋类 | 87% | **93%** | V4.1 +6.7pp |
| **可靠性** | 20% | **70%** | **V4.1 +50pp** |
| **实战** | 50% | **75%** | **V4.1 +25pp** |
| **总计** | **90.3%** | **90.3%** | **7 胜 7 负 120 平** |
| 耗时 | 3122s | **718s** | V4.1 快 4.3× |

**总分精确打平(121/134)。134 题里 120 题完全相同,各胜 7 题。**

**强项完全互补**:
- **本地模型的强项在执行** —— 多步工具调用(+40pp)、SQL 正确性、公文语体
- **云端的强项在判断** —— 抗幻觉、拒答、日期校准、实战要点覆盖

"API 应该全面超过本地"这个前提**不成立**。一个 35B MoE 微调版在数理代码指令上已经追平云端。

## 这个结论来之不易:判分器曾系统性偏袒"回答简短"的模型

V4.1 最初的 18 个失败里 **5 个是我的判分器 bug**,规律一致 ——
**答得越规范(写 LaTeX、加解释、用完整措辞),越容易被误判**:

| 题 | V4.1 实际回答 | 判分器 |
|---|---|---|
| `d3_prob_0094` | `rac{10}{21}` = 0.476 **正确** | 抽成 "10" 判错(不支持 LaTeX 分数) |
| `d10_reach_*` | 列出正确格子**并解释**"g1 被占不能走" | 把解释里的格子当**多报** |
| `d7_longqa` | "应提前**不少于30天**" | `30` 在中文旁失效 → 匹配失败 |
| `d8_cal_0028` | "2023 年 12 月" **正确** | 期望无空格的 "2023年12月" |

**5 处修复后重判:116/134 → 121/134(86.6% → 90.3%)。**

本地模型输出更简短,踩雷更少 —— 这是**与能力正相关的判分偏差**,最危险的一类。
**教训:判分器的容错必须覆盖模型实际会用的表达形式,而且要按"最强模型的输出"来测,不能按数据集标准格式。**

## 还有两处测试设计缺陷

**① D6 要求单轮吐出完整工具链** —— 但真实工具调用是多轮的(拿到文件内容才能写邮件)。
两个模型都"只调第一个工具",不是模型缺陷。改造成**真实多轮工具循环**后:
- DeepSeek D6: 30% → 79.5%
- 本地 35B D6: 60% → 87.2%

**② 部分 tool-decision 题在信息不全时要求硬调工具** —— 如"帮我订个周末的电影票"不给影片/场次，
认真的模型选择先确认反而扣分。另外工具定义只有名字、没有参数 schema。**已记录,未修。**

## 结论:证据不足

**两个探针都未达统计显著**,分歧题分别只有 3 题和 5 题 ——
**检验力太低,既不能证明污染,也不能排除**。

## ⚠ 方法边界

- **乱序探针**只能检测**位置记忆**(背"答案是 D")。模型若背的是**题干内容**,
  乱序测不出来 —— **乱序通过 ≠ 没有污染**。
- **改写探针**针对内容记忆,但改写质量依赖改写模型,改写可能无意改变题目难度。

## 同时修掉一个判定错误

第一版 `contamination.py` **只看指数、不看显著性**,把 5.3%(p=0.375)
报成"轻度疑似污染" —— 这是在噪声上滥用结论。已改为以统计显著性为准,
并在分歧题 <10 时直接说明"检验力不足"。

# 污染检测:决定性结论

## 样本量的作用(65 → 285 对)

| 配对 | 原题 | 探针 | 落差 | McNemar |
|---:|---:|---:|---:|---|
| 65 | 87.7% | 83.1% | 4.6pp | 4 对 1,p=0.375 |
| **285** | **82.5%** | **81.4%** | **1.1pp** | **9 对 6,p=0.607** |

**样本扩大 4.4 倍后落差从 4.6pp 掉到 1.1pp** —— 之前那个"信号"是噪声。
这正是统计层的价值:同样的数据,少一半样本会得出错误结论。

## 结论:可以排除重度污染,不能排除轻度

- 落差 95%CI = **[−1.4, +3.9]pp**
- **重度污染可排除**:靠记忆拿分的模型改写后落差通常 20pp+
- **轻度记忆效应(2–4pp)不能排除** —— 要收窄到 ±1pp 需要约 2,565 对,
  MMLU 只有 285 题,**这是该方法的天花板**

## 关键提速:精简 prompt

```bash
# 常规:24.5 秒/题,570 题需 3.9 小时
# 精简:1.65 秒/题,570 题只需 15.7 分钟
```

在 prompt 加「Do not explain, output exactly one line」后,输出从 381 token/题
降到 **4 token/题**。代价是绝对分从 87.7% 掉到 82.5%(去掉推理,能力确实降)。

**但污染检测看的是配对落差,两侧同条件 → 落差依然有效。** 这是能跑全量的关键。

## 修掉的对比脚本 bug

`contamination.py` 在原题与探针同处一个文件时会把**原题和它自己配对**(必然持平),
把落差稀释一半。已排除自配对。

# 断点续跑(2026-10-12)

## 为什么需要

一次全量跑可以到几小时:DeepSeek 跑 GPQA 198 题用了 **2.9 小时 / ¥14.63**。
旧 runner **只在全部跑完才写盘** —— 机器重启、系统睡眠、API 卡死,
整轮作废。切个显卡模式就能毁掉 3 小时的跑。

## 做法

`runner/checkpoint.py`:追加式 JSONL,每题写完立即 flush + fsync。

```python
ck = Checkpoint(suite, endpoint, [r["id"] for r in rows])
done = ck.load()                  # {id: record}
...
if qid not in done:               # 只跑没做过的
    ck.add(rec)                   # 立即落盘,杀进程也不丢
ck.clear()                        # 结果文件写好后才清理
```

**三个设计要点**:

1. **追加式**:一行一题。被强杀时文件在最后一题处仍完整可用
2. **残缺行容错**:断在半行的那条会被忽略,只是"这题还没做"
3. **按题集哈希隔离**:检查点 key = `suite__endpoint__sha1(题目id列表)`。
   换了子集或换了模型**不会串味**,自动从头跑

## 用法

```bash
# 默认自动续跑:发现同题集同端点的检查点就接着跑
python runner/run.py --endpoint local --suite calib

# 忽略检查点,从头重跑(并清掉旧检查点)
python runner/run.py --endpoint local --suite calib --no-resume
```

续跑时会明确提示:

```
  [resume] 从检查点恢复:100/133 题已完成,续跑剩余 33 题
           results\.ckpt\canary__mock__6093b1c327.jsonl
   10/133  (已从检查点跳过)
```

## 验证

| 测试 | 结果 |
|---|---|
| 写两条后正确读回 | ✓ |
| **残缺行被忽略**(模拟崩溃) | ✓ |
| 不同题集 → 不同 key | ✓ |
| 不同端点 → 不同 key | ✓ |
| clear 后文件消失 | ✓ |
| **端到端:伪造 100 题已完成 → 只跑剩余 33 题** | ✓ 133 = 100 + 33 |
| 结果落盘后自动清理检查点 | ✓ |
| `--no-resume` 忽略并清除旧检查点 | ✓ |
